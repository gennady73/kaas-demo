# RST-01–04 recovery qualification protocols

Revision 0.1. **PROPOSED, NOT EXECUTED.** Requirement SC3/SRS 4.5: no data loss and recovery within 10,800 seconds for every confirmed restart category. Qualification is specific to environment/version/configuration, dedicated/shared mode and explicitly agreed controlled/abrupt variant. An exploratory load run does not pass these cases. Destructive loss of every persistent copy is outside a restart assumption; unresolved coverage must remain visible.

## Shared execution contract

Before a later separately scoped run, C0/user authorizes exact category/variant/resources/window and run owner. C4 supplies reviewed fault/restoration actions for the installed operator and topology; this package contains no generic delete/restart command that could bypass GitOps. C1 supplies storage/placement and inherited evidence; C6 validates access/credential recovery; C5 supplies registry/Gravitino recovery order if in scope; C2 supplies bounded producers, buffering/retry/acks/idempotence/consumer policies and evidence; C3 freezes expected sets and acceptance.

Capture environment ID, versions/digests, source pins, metadata version/features (including ELR state), brokers/controllers/host and physical failure domains, PV/PVC mapping, storage class/reclaim and deleteClaim policy, per-topic RF/ISR/cleanup/size/retention, internal-topic RF/ISR, actual native acks/retries/timeouts, groups/reset/commit strategy and source-buffer ownership. Dev minISR2 and acks=all are recorded observations for selected configurations, never inferred from `offset 2`. RF2/minISR2/acks=all prevents affected writes at one ISR; distinguish expected unavailability from persistence failure. Three dual-role nodes also place quorum behavior within broker faults.

Define `t0` as first injected disruptive action or first observed service impact (whichever occurs first when observable). Record injection, detection, infrastructure-ready, process-ready, client-reconnected, caught-up and reconciled timestamps. Proposed conservative `t1` is restored reads/writes, healthy required quorum/replication, successful client reconnection, required backlog replay and final integrity reconciliation, sustained for a pre-agreed window (OPEN). Report infrastructure-ready→Kafka-ready separately; retain the whole t0→t1 interval for the 3h objective. C0/C3 must accept endpoints, stable window and controlled/abrupt variants before a qualification claim.

Freeze record sets: planned, attempted, positively acknowledged, ambiguous sends, received, durably processed and committed. Preserve original IDs/hashes/sizes plus topic/partition/offset where the client exposes them, per-group expected ownership and source queues. Reconcile every acknowledged ID in the required preservation contract, all in-flight outcomes, duplicates/replays and side effects. Receipt-before-commit permits replay after receipt and before commit; replay is not silently a loss or exactly-once business processing. Define external sink idempotence/transaction boundary with the application owner. Current xk6 wrapper lacks ACK offsets: use an approved source/client extension or alternative evidence plan; do not fabricate offsets or rewrite acceptance to fit it.

Record pre-outage oldest unread age and offsets; evaluate [retention/catch-up budget](capacity-and-evidence-budgets.md). Continuous durable consumption/accounting is needed across a >6h run; end-of-day reread cannot cover expired data. No offset reset to latest, internal-topic recreation, retention truncation, ISR reduction or unclean election is an automatic recovery step. Evidence gaps do not reduce the no-loss requirement.

## Per-category procedures

| ID / boundary | Staged procedure for later approved execution | Required observations / stop boundary |
| --- | --- | --- |
| RST-01 single broker | Freeze baseline and healthy ISR/quorum; generate/consume recorded traffic; C4 restarts exactly one identified broker process with selected controlled or abrupt method; restore same storage/identity; reconnect, catch up and reconcile | Actual affected partitions/controller role, ACK/error/ambiguous sets, source buffering, process/storage readiness and t0→t1. Stop further disruption on lost quorum, unexpected missing copies, evidence failure or shrinking retention margin. |
| RST-02 rolling | Record explicit broker order and role/quorum membership; execute one C4-controlled step; wait for current generation, full required ISR/quorum, settled reassignment and application progress before next step; reconcile each step and total | No concurrent broker disruption; preserve per-step and aggregate clocks, leader changes and tenant impact. Aggregate target proposal covers first action through final reconciliation, not just each individual restart. Abort next step on any failed prerequisite. |
| RST-03 full Kafka | Keep infrastructure/storage and evidence observation available; approved procedure stops/restarts all relevant Kafka brokers/controllers without deleting CRs/PVCs; preserve cluster/node IDs/metadata; restore using installed operator procedure | Quorum election/log recovery, internal topics/offsets, listener identity/trust, producer ambiguity/retries and group positions; full outage and catch-up within target. Collector-only replacement evidence is not this test. |
| RST-04 infrastructure | Attach DEP-PERSIST-01 owner/scope/evidence; coordinate observation of a suitable planned underlying cluster/storage/power restart or specifically authorized integration scenario; establish external evidence/clock/source buffering that survives it; infrastructure owner restores service; C4 recovers Kafka from preserved volumes, then replay/reconcile | Whole infrastructure+Kafka+replay clock, storage identities/survival, scope of power/cache/attach behavior and persistence boundary. Reuse inherited infrastructure tests; do not commission a duplicate destructive campaign as a load-test gate. Evidence in the same failed domain alone is insufficient. |

Shared deployments include at least two tenants with positive/negative ownership evidence and unaffected-tenant impact; dedicated mode covers each claimed deployment and common-resource contention. New C4 profile qualification is not inherited from the single dev cluster. C5 governance availability, compatibility and metadata consistency are separate joined assertions where required by the tenant workload.

## DEP-PERSIST-01 interface (OPEN source reference)

User-declared inherited dependency, not independently evidenced here. C1/infrastructure owner returns: supplying project/service and requirement/version; named accountable owner; storage/backend/interface/failure-domain scope; covered restart/power/storage/cache and excluded destruction conditions; survival guarantee/persistence acknowledgement boundary; restoration obligations/timing; accessible signed/tested evidence references/dates; applicability to selected Kafka PVs and target VSAN. C7 maps coverage; C0 accepts residual scope. gp3 sandbox observations and future ODF neither supply nor supersede that contract. Missing references do not block offline work or impose duplicate durability testing before a load-only pre-flight.

## Result contract

C3 produces one result per category/variant/environment/mode: actual command/change receipts and authorization reference, exact source/config/identity, timestamps and recovery duration, workload budget/record sets/offset reconciliation, infrastructure evidence reference, metrics/alerts/client outcomes and complete raw custody manifest. PASS requires the approved no-loss contract, <=10,800s, required health/replay/stability and complete evidence. Unsent volume and expected write blocks are reported separately. A FAIL/INCONCLUSIVE cannot be promoted on counts, a healthy Pod, inherited storage claim or successful Git sync alone. Re-entry after any unexpected gap is a new reviewed scenario, preserving earlier evidence.
