# Offline GitOps project and application templates

`application-set.yaml.template` is a pair of AppProject and Application documents for each rendered scope; it is not an ApplicationSet CR/controller. Platform projects permit only Kafka/KafkaNodePool. A separate project for each tenant permits only KafkaTopic/KafkaUser. Repository, revision, destination and sync groups are explicit inputs. No automated sync, prune option, resource-deletion finalizer, test hook or Application-of-Applications is generated.

Project roles propose only get/sync on their own project Applications. These documents do not grant Kubernetes controller rights, configure SSO, remove global ArgoCD privileges or stop an already privileged actor editing projects/Applications. A manual sync permission alone cannot enforce a no-prune policy; later bootstrap/controller permissions and authorized workflow must enforce deletion controls. AppProject kind restrictions do not constrain ACL contents, topic names, or source paths within a repository. The offline validator checks those generated contents; Git protections and any admission/CI integration are not installed.

Candidate Kafka and tenant application resources exclude current dev, operator and control-plane namespaces. AppProject/Application metadata may use the existing openshift-gitops namespace; that exception does not authorize workload placement or namespace creation there. Recorded existing kaas-demo, kaas-demo-kafka and kaas-demo-operator project/Application names are protected against candidate reuse; other collisions require later live discovery. A later promotion design must review actual destinations, operator watch scope, controller RBAC, namespace ownership and policy integration; these review objects must not be applied as a dev ownership transfer. Cached Kafka schemas validate Kafka CRs; ArgoCD objects receive exact local policy/content checks only, not ArgoCD CRD/server validation.

`bootstrap-inputs.json` version 0.2 reuses the recorded existing ArgoCD namespace/controller identity and Kafka operator/namespace-watch baseline. Provenance and observation dates are in `bootstrap-reference-evidence.json`; these are not fresh live facts. Candidate targets, watch mechanism/version evidence, namespace owner and authority/delivery/deletion references remain unresolved. The input is a plan, not a Kubernetes resource or an execution-ready bootstrap configuration.

`policies/tenants/bootstrap_tool.py` validates this plan against a profile and can validate an exact local Namespace/Role/RoleBinding proposal. Only candidate Kafka/app namespaces and six non-delete verbs on four Kafka kinds are admitted. It rejects known protected dev/control-plane namespace edits, elevated bindings, Secrets, OperatorGroup/Subscription changes and extra resources. Actual candidate namespace existence/ownership still requires later verification. Watch-scope validation checks a declared proposal for preservation/coverage; it does not establish installed version support, real watch state or effective permissions.
